# AI 日报 · Dify 工作流

> 抓取 AI 领域资讯 → 去重打分 → 生成中文简报 → 推送到飞书群

一个基于 [Dify](https://dify.ai) **Workflow** 构建的每日资讯聚合流水线。
**9 个节点 · 8 个数据源**，全部可视化编排，导出的 DSL 可直接导入复现。

---

## 它做什么

**输入**：无。源列表写在工作流内部，运行时不需要填任何参数。

**输出**：

- 一份中文 Markdown 简报（20 条，每条 4-5 句 + 原始链接）
- 推送到飞书群

**主要能力**：

| 能力 | 说明 |
|---|---|
| 多源聚合 | 8 个源：AI 媒体 5 个 + GitHub 热榜 + arXiv 论文 |
| 归一化去重 | 链接与标题双归一化；来源名按域名自动推断 |
| 时间窗过滤 | 只保留 48 小时内的条目 |
| 模型打分 | 按技术含量 / 行业影响 / 时效性三维打分，同时分类与合并重复 |
| 配额控制 | 同一分类最多 6 条，防止论文或开源项目刷屏 |

## 架构

### 节点一览

| # | 节点 | 类型 | 职责 |
|---|---|---|---|
| 0 | 开始 | Start | 无输入变量 |
| 1 | 源列表 | 代码 | 输出源地址数组（**唯一需要改源的地方**） |
| 2 | 抓取 | 迭代 + RSS Reader | 逐个源抓取；单源失败不影响其他源 |
| 3 | 归一化去重 | 代码 | 摊平 → 时间窗过滤 → 去重 → 推断来源名 |
| 4 | 批量打分 | LLM | **一次**调用给所有条目打分 + 分类（`deepseek-chat`） |
| 5 | 合并排序 | 代码 | 把打分结果与原文按 `id` 合并 → 排序 → 取 Top 20 |
| 6 | 生成简报 | LLM | 生成 Markdown 简报（`qwen-plus`） |
| 7 | 清洗 | 代码 | 剥掉可能混进正文的 `<think>` 思维链，只留 Markdown |
| 8 | 推飞书 | HTTP | POST 到飞书群机器人 webhook |

### 数据流

```
（无输入）
  → 代码写出源地址数组                 feeds  : Array[String]
  → 迭代逐个抓取 RSS / Atom            output : Array[Object]
  → 代码归一化 / 去重 / 48 小时预筛     items  : String(JSON)
  → LLM 批量打分（一次调用）            text
  → 代码按 id 合并原文 + 排序取 Top 20   items  : String(JSON)
  → LLM 生成简报                       text
  → 代码 清洗（剥掉思维链）             text
  → 推送到飞书群（HTTP）
```

### 依赖的插件

| 插件 | 用途 |
|---|---|
| `remywwo/rss-reader` | 抓取 RSS / Atom 订阅源 |

## 快速开始

### 1. 前置要求

- Dify **1.10.0 或更高**（本工作流用了部分较新的节点能力）
- 一个飞书群（用来收简报）
- 任意 OpenAI 兼容的模型供应商（示例用 DeepSeek + 通义千问）

### 2. 导入

Dify 工作室 → 创建应用 → **导入 DSL 文件** → 选择本仓库的 `.yml`。

导入后**不要急着运行**，先完成下面的必配项。

### 3. 必配项（导入者必读）

> ⚠️ **导入的是一份"不完整"的应用。** 下面这些东西**不会**随 DSL 文件迁移，必须手动配置。

#### 3.1 环境变量（一个，**必须选 `Secret` 类型**）

| 变量名 | 类型 | 填什么 |
|---|---|---|
| `FEISHU_WEBHOOK` | **Secret** | 飞书群机器人 webhook 完整地址 |

**获取飞书 webhook**：飞书群 → 设置 → 群机器人 → 添加机器人 → **自定义机器人**
→ 安全设置选「**自定义关键词**」，关键词填 `日报` → 复制 webhook 地址。

> **为什么类型必须是 `Secret`**：`String` 类型的值在导出 DSL 时是**明文**的。
> 选 `Secret` 才会被脱敏。这一点在你自己重新发布时同样重要。

> **关键词为什么是 `日报`**：飞书的关键词校验是**精确字符串匹配**。
> 简报标题是 `# AI 日报 · 2026-10-12 周一`，`日报` 两个字一定在正文里，
> 而且不带空格、不会有歧义。

#### 3.2 模型供应商

**API Key 不随 DSL 迁移。** 请在「设置 → 模型供应商」里配置，并确认节点里选的模型名可用：

| 节点 | 建议模型 | 选型理由 |
|---|---|---|
| 节点 4 · 批量打分 | `deepseek-chat` / `qwen-turbo` | 判别任务，用便宜的 |
| 节点 6 · 生成简报 | `qwen-plus` 及以上 | 生成任务，用稍强的 |

> ⚠️ **这两个节点都不要用推理模型**（`deepseek-reasoner` / R1 等）。
> 它们会把思维链写在 `<think>...</think>` 里一起输出：
> 打分节点会被污染导致 JSON 解析失败；生成节点会把"内心独白"直接推进飞书群里。

#### 3.3 装插件

Dify 左侧「插件」→ 右上角「安装插件」→ **Marketplace**：

| 搜索关键词 | 装哪个 |
|---|---|
| `rss` | `remywwo/rss-reader` |

#### 3.4 检查节点引用

导入后逐个打开节点，确认变量引用没有报错（导入到新环境时节点 ID 会变）。重点看：

- 节点 8 的 URL 是否指向 `FEISHU_WEBHOOK`

### 4. 运行

在编排页点右上角 **「运行」**。第一次跑建议去 **「追踪」** 里逐节点看一遍输入输出，
确认数据是通的。

| 源 | 地址 | 格式 | 语言 | 精准度 |
|---|---|---|---|---|
| 量子位 | `https://www.qbitai.com/feed` | RSS | 中 | AI 专用 |
| OpenAI News | `https://openai.com/news/rss.xml` | RSS | 英 | AI 专用 |
| GitHub 热榜 | `https://rsshub.rssforever.com/github/trending/daily/any` | RSS | 英 | 开源项目 |
| arXiv 论文 | `https://export.arxiv.org/api/query?search_query=cat:cs.AI&...` | **Atom** | 英 | 论文 |
| 雷锋网 | `https://www.leiphone.com/feed` | RSS | 中 | 泛科技 |
| InfoQ 中文 | `https://www.infoq.cn/feed` | RSS | 中 | 泛技术 |
| IT之家 | `https://www.ithome.com/rss/` | RSS | 中 | 泛科技 |
| TechCrunch | `https://techcrunch.com/feed/` | RSS | 英 | 泛科技 |

**更改数据源**：只需改**节点 1** 里的数组。如果新增的源不在 `节点 3` 的域名映射表里，
记得同步加一行，否则简报里的来源名会显示成裸域名。

**两个踩过的坑**（写在这里省得你也踩）：

- **arXiv 的 RSS 版是空壳**：`export.arxiv.org/rss/cs.AI` 返回 891 字节、零个 `<item>`，
  而且周末不更新。**必须用 API 版**（返回 Atom，插件支持）。
- **源的可达性会变**：同一批 URL 在不同时间测结果可能不同。
  **配之前一定要在运行环境里重测一遍**，判据不只看状态码，还要看内容：

  ```bash
  curl -sL -m 10 -A "Mozilla/5.0" "$URL" | head -c 200
  ```

  只认开头是 `<rss` / `<feed` / `<?xml` 的。返回 HTML 说明这个 RSS 已经失效了。

## 设计决策

### 为什么用 Workflow，不用 Agent

采集 → 去重 → 打分 → 生成，这条链路的**分支完全可穷举**，单次错误代价也低。

Agent 的价值在于处理"设计时想不到的情况"。这里没有这种情况，
上 Agent 只会引入不确定的执行路径，换不来任何新能力，而且成本和延迟都会上去。

**判据**：如果你能在纸上画完这个任务的所有分支，就不需要 Agent。

### 为什么分两档模型

打分是**判别任务**（给已有内容评一个分），不需要强模型；
生成是**创作任务**，需要语言能力。用一个大模型全包是浪费。

两档模型的差价是这类流水线里最容易拿到的成本优化。

### 为什么节点 5 要"把原文合并回来"

节点 4 的模型只被要求返回 `id / score / category / reason`——
**原文的标题、链接、摘要它并不返回**。

如果下游只拿到打分结果，写简报时就只剩 `reason` 那 20 个字可用，
摘要会变得又空又像编的。所以节点 5 按 `id` 把节点 3 的原文 join 回来，
**原文信息直接流转，不经过模型的转述**。

### 为什么打分要"一次调用批量处理"

20 条各调一次模型 = 20 次请求。批量放进同一个 Prompt 里 = 1 次请求。
在这个规模下，批量既快又便宜，而且模型能看到全局，去重判断也更准。

## 已知限制

- **无定时触发**。当前是手动运行。要自动化需要加 Schedule Trigger
  （仅 Dify 1.10+ 支持，且只支持 Workflow 应用），并保证宿主 7×24 在线。
- **单次运行时间约 10-30 秒**，取决于源站响应速度。
- **简报较长**（20 条 × 4-5 句 ≈ 3000 字以上），在手机端阅读体验一般。
- **飞书 `text` 消息不渲染 Markdown**，标题的 `#` 会原样显示。
  要排版好看得换成 `interactive` 卡片（`lark_md` 元素支持加粗和链接）。
- **GitHub 热榜走的是公共 RSSHub 实例**，该实例可能限流或失效。
  备选是 GitHub 官方 Search API，但返回 JSON，需要另加 HTTP 节点解析。
- **不做历史去重**：每次运行都是独立的一轮，不记得昨天推送过什么。
  如果同一事件连续两天上榜，会被推两次。
- **论文源未做主题过滤**：`max_results=30` 拉的是 cs.AI 全量最新，
  靠打分和配额筛，不做领域细分。
